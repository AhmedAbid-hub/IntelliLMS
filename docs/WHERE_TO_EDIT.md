## How to use this directory

Search this file for the visible feature or symptom. Each row gives **feature → frontend → API → backend → model → tests**. API paths are relative to `/api/v1/`; placeholders such as “affected resource” are deliberately contextual rather than invented endpoints. A backend file often covers several pages; a shared frontend file often serves several roles.

The “start here” note identifies the first useful investigation and adjacent behavior affected. Full per-route details are in [frontend map](FRONTEND_PAGE_MAP.md); complete endpoint methods/contracts in [backend map](BACKEND_CODE_MAP.md); role restrictions in [permission map](ROLES_AND_PERMISSIONS_MAP.md). All listed features already exist unless explicitly described otherwise.

## Change discipline

Read [AGENTS.md](../AGENTS.md), the latest [progress](../IMPLEMENTATION_PROGRESS.md) and the exact affected permission tests. Preserve unrelated Git changes. Prefer the existing service for a domain rule, rather than a second implementation inside a UI handler. Add relevant positive/negative coverage when behavior changes; for backend changes run checks/pytest, for frontend changes run typecheck/Vitest/build, plus affected browser journeys. Never reset the live database to make a test pass.

This handbook itself changes documentation only. Static findings awaiting a separate implementation task are listed in [roles-map discrepancies](ROLES_AND_PERMISSIONS_MAP.md#discrepancies-and-boundaries).
